YMCA Wellness Café API

A reward-ledger service on the Rubix chain. Register an account, authenticate with a bearer token, register activities, and pay out rewards across ten admin nodes.

01Getting started

Create an account once. After that, generate a token whenever you need one and send it on every request.

Once, per account

Registration is open — no token required. Password must be at least 8 characters. You only ever do this again if you want a second account.

curl -X POST https://yqa.rubix.network/api/auth/users \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"your-password"}'

Every run — generate a token

Post your credentials, get a fresh access token valid for 15 minutes. There is no session to keep alive — call it again whenever you need another, and an earlier token stays valid until it expires on its own.

TOKEN=$(curl -sS -X POST https://yqa.rubix.network/api/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"your-password"}' \
  | jq -r '.access_token')

Every request — send the token

curl https://yqa.rubix.network/api/queue/metrics \
  -H "Authorization: Bearer $TOKEN"

That is the whole authentication story for a typical job. The refresh token in the login response is optional: it exists so a job running longer than 15 minutes can extend without re-sending credentials. A job that finishes inside 15 minutes can ignore it and simply generate a new token next run.

With a token in hand, the reward flow is two calls: register an activity (§3) to bind an ID to a point value, then transfer a reward (§4) naming that activity, which returns a request_id you poll until it settles.

02Authentication

RS256 JWTs. Send Authorization: Bearer <access_token> on every protected call.

POST/api/auth/usersno auth · once

Creates an account. Emails are case-insensitive and unique. Run this once per account, not per request.

{"email":"clientteam@rubix.net","password":"clientcron2026"}

201 {"status":true,"data":{
  "id":"f8f82dc3-3d98-4ff0-a7d6-0365b20b6e22",
  "email":"clientteam@rubix.net","role":"operator",
  "created_at":"2026-08-25T07:51:11.673478Z"}}

400 password under 8 chars, or malformed email · 409 email already registered

POST/api/auth/tokenno auth · per run

Generates a token pair. Call it as often as you need — nothing is stored between calls, and a new access token does not invalidate an earlier one. /api/auth/login is an alias for this same endpoint; both are supported, neither is deprecated.

{"email":"clientteam@rubix.net","password":"clientcron2026"}

200 {"access_token":"eyJhbGci...","refresh_token":"...",
     "expires_in":900,"token_type":"Bearer"}

Note the response is flat — read .access_token, not .data.access_token. expires_in is seconds.

POST/api/auth/refreshno auth

Exchanges a refresh token for a new access + refresh pair.

{"refresh_token":"..."}

200 {"access_token":"...","refresh_token":"...",
     "expires_in":900,"token_type":"Bearer"}

Refresh tokens rotate — reuse revokes everything

Each refresh consumes the old token and issues a new one. Presenting a spent refresh token returns 401 and revokes every active refresh token for that account, forcing a full re-login.

Two jobs sharing one account will knock each other out. Give every cron job its own account.

GET/api/auth/me
200 {"status":true,"data":{"id":"...","email":"...",
     "role":"operator","created_at":"..."}}
POST/api/auth/logout

Revokes one refresh token, or all sessions with {"all":true}. Does not invalidate access tokens already issued — those expire on their own.

{"all":true}   →   200 {"status":true,"message":"all sessions revoked"}

03Activities

An activity binds an ID to a point value for one admin DID. Reward transfers sum the points of the activity IDs you name.

POST/api/activity/add

Writes to the admin's add_activity contract chain. Synchronous — expect 1–3 s.

{"admin_did":"bafybmicvcv...w3uu",
 "activity_id":"swim-100",
 "reward_points":25,
 "description":"100m swim"}

200 {"message":"Activity added to smart contract tokenchain",
     "data":{"contract_hash":"QmT4qVPVPN...",
             "transaction_id":"fb334558f0c8...",
             "message":"Transaction ... completed successfully"}}

activity_id is yours to choose, and is unique per admin. Re-posting the same ID succeeds and updates the stored activity — it does not create a second one, so reward points cannot double-count. Each call does append an entry to the contract chain, so the full history stays auditable.

04Reward transfers

The only asynchronous endpoint. Transfers queue per admin DID — serialized within one admin, parallel across the ten.

POST/api/rewards/transfer

activity_id is an array. Points are summed across the listed activities.

{"user_did":"bafybmie4zt...qi5i",
 "admin_did":"bafybmicvcv...w3uu",
 "activity_id":["swim-100"]}

202 {"status":true,
     "message":"Transfer request queued for processing",
     "data":{"request_id":"00387b67-a2ce-4046-ae29-0d79893c0d2c"}}
GET/api/rewards/status/:request_id
200 {"status":true,"data":{
  "request_id":"00387b67-...","status":"success",
  "reward_points":25,"activity_ids":["swim-100"],
  "transaction_id":"619e1457d16c92ab...",
  "contract_hash":"QmdtEWSHnUug1...",
  "message":"transferred 25 ytoken to bafybmie4zt...",
  "error_details":"","kind":"reward",
  "created_at":"2026-08-25T07:52:39Z","updated_at":"..."}}
  • queued — accepted, waiting on the admin's worker
  • processing — worker is blocked on Rubix quorum signing
  • success — settled; transaction_id is populated
  • failed — see error_details

Unknown IDs return 404 {"error":"Transfer not found"}. In testing a transfer settled in under 4 seconds; poll every 2–3 s and allow for longer if quorum is slow.

05History and mappings

Both history endpoints wrap their list in an object with a count — they do not return a bare array.

GET/api/rewards/user/:user_did
200 {"status":true,"data":{
  "user_did":"...","count":3,
  "rewards":[{"activity_ids":["swim-100"],"reward_points":25,
    "admin_did":"...","user_did":"...",
    "transaction_id":"619e1457...","date":"2026-08-25T07:52:39Z"}]}}
GET/api/rewards/admin/:admin_did
200 {"status":true,"data":{"admin_did":"...","count":3,"rewards":[...]}}
GET/api/users/:user_did/admin

Returns the admin that onboarded a user. Only populated by /api/create-did-with-pubkey — a user who received rewards without being minted through that endpoint returns 404 {"error":"no admin mapping for user"}. The same applies to the user count below, which reads the same table.

GET/api/admins/:admin_did/users/count
200 {"status":true,"data":{"admin_did":"...","user_count":0}}
GET/api/queue/metrics

Queues are created lazily on an admin's first transfer, so total_admins counts admins that have been used, not the ten configured.

200 {"status":true,"data":{
  "admin_queues":[{"admin_did":"bafybmicvcv...","queue_size":0}],
  "total_admins":1,"total_queued":0}}
GET/api/healthno auth
200 {"admins":10,"ft_name":"ytoken","status":"ok"}

06Contracts

All thirty contracts — ten admins × reward, add_activity, add_admin — are already deployed. These endpoints are for reading chains and running ad-hoc executions.

GET/api/contracts/:admin_did/:kind/chain

kind is reward, add_activity, or add_admin. Returns the chain entries as an array under data.

GET/api/contracts/by-hash/:contract_hash/chain

Same, addressed by contract hash directly.

POST/api/execute-contract

Field names differ from the deploy endpoint — it is executor_did and contract_input.

{"executor_did":"bafybmicvcv...w3uu",
 "contract_hash":"QmdtEWSHnUug1...",
 "contract_input":"{\"probe\":\"apitest\"}"}

200 {"message":"DApp executed successfully",
     "data":{"Success":true,"transaction_id":"fe6f05f565..."}}
POST/api/deploy-contract

Takes deployer_did, kind, wasm_path, lib_path. Paths resolve on the server. Re-deploying an existing contract fails with 502 rather than being idempotent — you should not need this endpoint.

Errors are shaped {"status":false,"error":"...","message":"..."}. One quirk worth handling: an unknown admin_did on /api/activity/add returns 500 with "admin has no add_activity contract" rather than a 404. Validate admin DIDs against your own list before calling.

08Running from cron

  • One account per job. Refresh-token rotation means concurrent jobs on a shared account revoke each other. This is the single most common way to break the integration.
  • Generate a token per run for jobs that fire less often than every 15 minutes — simpler than persisting a refresh token, and avoids rotation entirely.
  • Refresh on 401 only for jobs that run longer than a token's 15-minute life; otherwise just generate a new token.
  • Allow long timeouts. Chain writes block on quorum signing. The gateway permits 300 s; set your client's timeout to match rather than the usual 30 s.
  • Spread load across admin DIDs. Transfers serialize per admin, so ten concurrent payouts on one admin queue up while ten across ten admins run in parallel.
#!/usr/bin/env bash
set -euo pipefail
BASE=https://yqa.rubix.network

TOKEN=$(curl -sS -m 30 -X POST "$BASE/api/auth/token" \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"$YMCA_EMAIL\",\"password\":\"$YMCA_PASSWORD\"}" \
  | jq -er '.access_token')

REQ=$(curl -sS -m 60 -X POST "$BASE/api/rewards/transfer" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"user_did\":\"$USER_DID\",\"admin_did\":\"$ADMIN_DID\",
       \"activity_id\":[\"swim-100\"]}" \
  | jq -er '.data.request_id')

for _ in $(seq 20); do
  S=$(curl -sS -m 30 "$BASE/api/rewards/status/$REQ" \
        -H "Authorization: Bearer $TOKEN" | jq -r '.data.status')
  case "$S" in
    success) echo "ok $REQ"; exit 0 ;;
    failed)  echo "failed $REQ" >&2; exit 1 ;;
  esac
  sleep 3
done
echo "timeout waiting on $REQ" >&2; exit 1

Test environment — two things to know

Registration is open. Anyone who can reach the host can create an account, and every account holds the full API surface across all ten admin DIDs. Acceptable for this test deployment; it will be restricted before production.

Reward transfers do not move tokens yet. The fungible-token leg is currently disabled server-side. A transfer settles with status: success and a real transaction_id, and the audit record is written to the contract chain — but no ytoken balance changes. Build and test against the request/status contract; balances will start moving once the FT leg is enabled, with no change to this API.
