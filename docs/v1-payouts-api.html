Wellness Café Payouts API

01Getting a token

All seven endpoints require Authorization: Bearer <access_token>. This is the one addition to the original contract — everything else matches.

Once, per account

Registration is open. Password must be at least 8 characters. You only do this again if you want a second account.

curl -X POST https://yqa.rubix.network/api/auth/users \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"your-password"}'

Every run — generate a token

Post credentials, get a token valid for 15 minutes. No session is established: call it whenever you need one, and earlier tokens stay valid until they expire.

TOKEN=$(curl -sS -X POST https://yqa.rubix.network/api/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"your-password"}' \
  | jq -r '.access_token')

The response is flat — read .access_token, not .data.access_token. /api/auth/login is an alias for the same endpoint.

Every request — send the token

curl "https://yqa.rubix.network/admin/activity/list" \
  -H "Authorization: Bearer $TOKEN"

One account per job

The login response also carries a refresh_token, which you only need for a job running longer than 15 minutes. Refresh tokens rotate: presenting a spent one returns 401 and revokes every active refresh token for that account.

Two jobs sharing an account will knock each other out. Give each its own — or skip refresh entirely and generate a fresh token per run.

02The reward flow

Four calls, in this order. Steps 1 and 2 are setup and only repeat when you onboard a new user or add a new activity type.

  1. Create the user's DID

    POST /createdid — mints a DID from the user's public key on an admin's node, and records which admin owns them.

  2. Register the activity

    POST /admin/activity/add — binds an activity ID to a point value for that admin.

  3. Queue the payout

    POST /admin/payouts — returns 202 and a request_id. Points are summed across the activity IDs you name.

  4. Poll until it settles

    GET /admin/payouts/status/:request_id — until status is success or failed.

Create the DID through /createdid before paying anyone. A payout to a DID that was never created through that endpoint still succeeds, but the user has no admin mapping, so GET /users/:user_did/payouts and the user-to-admin lookups will not find them.

03Users

POST/createdidsync

Creates a user DID on the admin's Rubix node from an uncompressed secp256k1 public key — 04 followed by 128 hex characters. Also records the user→admin mapping.

{"admin_did":"bafybmicvcv...w3uu",
 "public_key":"046dfd30bc498a825f...12d526fc"}

200 {"did":"bafybmiap7cpgjs3s3hr4qfje37itwb6t5cmik7xjnbbtdys5wcdx3tzudm"}

The node validates the key is on-curve. A malformed or wrong-length key returns 502. Note the response here is a bare object, not the {status, message, result} envelope.

GET/users/:user_did/payoutssync

Returns the user's fungible-token holdings, aggregated by creator admin.

200 {"status":true,
     "message":"Got FT info successfully",
     "ft_info":[{"creator_did":"bafybmicvcv...w3uu",
                 "ft_name":"ytoken","ft_count":15}],
     "result":null}

Read ft_info, not result — result is always null on this endpoint. A user with no mapped admin returns an empty ft_info.

04Activities

POST/admin/activity/addsync · on-chain

Writes to the admin's activity contract chain and stores the activity. Takes 1–3 seconds.

{"admin_did":"bafybmicvcv...w3uu",
 "activity_id":"cycle-5k",
 "reward_points":15,
 "description":"5km cycle"}

200 {"status":true,
     "message":"Activity added successfully",
     "result":[{"BlockId":"241ee2ced0fc5aee...","BlockNo":null,
                "Epoch":null,
                "SmartContractData":"{\"activity_id\":\"cycle-5k\",\"reward_points\":15}"}]}

activity_id is yours to choose and is unique per admin. Re-posting the same ID updates the activity rather than creating a second one, so points cannot double-count — though each call does append a chain entry, keeping the history auditable.

GET/admin/activity/listsync

Optional ?admin_did= filter. Returns a bare array — no envelope, unlike the other endpoints here.

GET /admin/activity/list?admin_did=bafybmicvcv...w3uu

200 [{"activity_id":"yoga-001","reward_points":10,
      "block_hash":"36e40f144977e464..."},
     {"activity_id":"swim-100","reward_points":25,
      "block_hash":"5053075f78986500..."},
     {"activity_id":"cycle-5k","reward_points":15,
      "block_hash":"241ee2ced0fc5aee..."}]

block_hash is the transaction that recorded the activity on-chain. Activities created before this field existed return "".

05Payouts

The only asynchronous pair. Payouts queue per admin DID — serialized within one admin, parallel across the ten.

POST/admin/payoutsasync · 202

activity_id is an array. Points are summed across the activities listed.

{"user_did":"bafybmiap7c...zudm",
 "admin_did":"bafybmicvcv...w3uu",
 "activity_id":["cycle-5k"]}

202 {"status":true,
     "message":"Transfer request queued for processing",
     "result":{"request_id":"8eb60a34-4678-4f5b-a033-0d746afa61b2"}}
GET/admin/payouts/status/:request_idpoll
200 {"status":true,
     "message":"transferred 15 ytoken to bafybmiap7c...zudm",
     "result":{
       "request_id":"8eb60a34-...","status":"success",
       "reward_points":15,"activity_ids":["cycle-5k"],
       "user_did":"bafybmiap7c...zudm","admin_did":"bafybmicvcv...w3uu",
       "block_id":"1e24967b21f7a00c...",
       "blockchain_tx_id":"1e24967b21f7a00c...",
       "ft_transfer_txid":"1e24967b21f7a00c...",
       "contract_hash":"QmdtEWSHnUug1...",
       "started_at":"2026-08-25T08:26:09Z",
       "completed_at":"2026-08-25T08:26:10Z",
       "queued_at":"","error_details":""}}
  • queued — accepted, waiting on the admin's worker
  • processing — signing in progress on the chain
  • success — settled; the transaction id fields are populated
  • failed — see error_details

block_id, blockchain_tx_id, and ft_transfer_txid all carry the same transaction id — the unified transaction covers what were previously separate legs. queued_at is always ""; use started_at. A payout settled in about one second in testing; poll every 2–3 s.

06Admins

POST/admin/user/addsync · on-chain

Appends an admin DID to an existing admin's chain. This is an on-chain record only — it does not make the new DID usable for payouts. Ten admins are already provisioned; you should not normally need this.

{"new_admin_did":"bafybmie4zt...qi5i",
 "existing_admin_did":"bafybmicvcv...w3uu"}

200 {"status":true,
     "message":"Fetched latest block smart contract data",
     "result":[{"BlockId":"34b7e25a6d834ced...",
                "ExecutorDID":"bafybmicvcv...w3uu",
                "SmartContractData":"{\"add_admin\": {\"admin_did\":\"bafybmie4zt...qi5i\"}}",
                "BlockNo":null,"Epoch":null,
                "InitiatorSignature":null,"InitiatorSignData":null}]}

ExecutorDID echoes the existing admin that signed the write.

07Responses and errors

Envelope shapes vary

Most endpoints return {status, message, result}, but three do not. Check the per-endpoint examples rather than assuming:

EndpointRead the payload from
/createdidtop level — {"did": "..."}, no envelope
/admin/activity/listtop level — a bare array
/users/:did/payoutsft_info — result is always null
everything elseresult

Fields that are always empty

BlockNo, Epoch, InitiatorSignature, and InitiatorSignData are returned as null, and queued_at as "". They are preserved so existing response destructuring keeps working, but carry no data. Do not branch on them.

Status codes

CodeMeaningWhat to do
200Success—
202Payout queuedPoll the status endpoint
400Validation failedRead error; fix the payload
401Missing or expired tokenGenerate a new token
404Unknown request id or userCheck the identifier
500Server or contract lookup failureRead message
502Rubix node rejected the callRetry; escalate if it persists

An unknown admin_did returns 500 with "admin has no add_activity contract" rather than a 404. Validate admin DIDs against your own list before calling.

08Running from cron

  • One account per job. Refresh-token rotation means concurrent jobs on a shared account revoke each other — the most common way to break this integration.
  • Generate a token per run for jobs firing less often than every 15 minutes. Simpler than persisting a refresh token, and avoids rotation entirely.
  • Allow long timeouts. Chain writes block on signing. The gateway permits 300 s — set your client to match rather than the usual 30 s.
  • Spread load across admin DIDs. Payouts serialize per admin, so ten payouts on one admin queue up while ten across ten admins run in parallel.
#!/usr/bin/env bash
set -euo pipefail
BASE=https://yqa.rubix.network

TOKEN=$(curl -sS -m 30 -X POST "$BASE/api/auth/token" \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"$YMCA_EMAIL\",\"password\":\"$YMCA_PASSWORD\"}" \
  | jq -er '.access_token')

REQ=$(curl -sS -m 60 -X POST "$BASE/admin/payouts" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "{\"user_did\":\"$USER_DID\",\"admin_did\":\"$ADMIN_DID\",
       \"activity_id\":[\"cycle-5k\"]}" \
  | jq -er '.result.request_id')

for _ in $(seq 20); do
  S=$(curl -sS -m 30 "$BASE/admin/payouts/status/$REQ" \
        -H "Authorization: Bearer $TOKEN" | jq -r '.result.status')
  case "$S" in
    success) echo "ok $REQ"; exit 0 ;;
    failed)  echo "failed $REQ" >&2; exit 1 ;;
  esac
  sleep 3
done
echo "timeout waiting on $REQ" >&2; exit 1

Test environment — two things to know

Registration is open. Anyone who can reach the host can create an account, and every account holds the full API surface across all ten admin DIDs. Acceptable here; it will be restricted before production.

Payouts do not move tokens yet. The fungible-token leg is disabled server-side. A payout settles with status: success and real transaction ids, and the audit record is written to the chain — but no ytoken balance changes. Build against the request and status contract; balances will start moving once the leg is enabled, with no change to this API.
